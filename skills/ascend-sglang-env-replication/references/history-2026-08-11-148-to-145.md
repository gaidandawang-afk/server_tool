# Historical flow: replicate Ascend SGLang SSH environment 148 → 145 (2026-08-11)

This is the exact successful flow used to stand up the Ascend SGLang SSH container
`/data2` runtime on host `80.48.33.145` by copying the working reference environment on
`80.48.33.148`. Follow it in order. Negative events are inlined at the step where they
first occurred, marked **[PITFALL]**.

Key environment facts used throughout (verified, not guessed):

- Both hosts root ssh `80.48.33.145` / `80.48.33.148`; the challenge was the container
  SSH port differs from the default (`6222` on the SSH container, host-network mode).
- Ascend stack: CANN 9.0.0, driver, `torch` 2.10.0 + `torch_npu` 2.10.0, Python 3.11.15,
  16× Ascend910_9382 per node.
- Container base image: `quay.io/ascend/sglang:v0.5.13.post1-cann9.0.0-a3` (ai on 148).
- The shared dependency layout: CUDA kernels live under `/data2/iws/deps/sglang-kernel`
  (cu130-cp312); NPU kernels live under `/data2/iws/deps/sgl-kernel-npu` (a3-cp311);
  built wheels under `/data2/iws/builds/`.

## Step 1 — Locate the reference environment and its image

The reference environment that already works is on `80.48.33.148`. Identify the target
SSH container image and its base image before transferring anything.

**[PITFALL]** The container SSH setup differs from a normal `-p` publish mapping. On the
reference, the container runs in host-network mode and its sshd listens on a dedicated
port (e.g. `6222`) directly, not on port 22 via a publish rule. Check the actual
`sshd_config` (`Port`, `PermitRootLogin`, password vs key) before assuming how to reach it.

## Step 2 — Transfer the full image 148 → 145

There is a 15.9 GB container image to move. Use `docker save` + transfer + `docker load`,
and verify integrity with `sha256sum` after the move.

```bash
# On the reference host where the image already exists:
docker save sglang-ssh:v0.5.13.post1-cann9.0.0-a3 | gzip > /tmp/sglang-ssh.img.gz
sha256sum /tmp/sglang-ssh.img.gz > /tmp/sglang-ssh.img.sha256

# Transfer (145 had free ssh to 148; scp the archive).
scp root@80.48.33.148:/tmp/sglang-ssh.img.gz root@80.48.33.145:/tmp/

# On the target host:
docker load < /tmp/sglang-ssh.img.gz
```

**[PITFALL]** `docker save` output is very large; check disk space on both hosts and on
the transfer path before starting. Verify the archive hash before `docker load` so a
corrupt transfer is caught early.

## Step 3 — Build / recreate the persistent data root on the target

The tooling and persistence boundary assume `/data2`, but the target host did not have a
`/data2` path yet.

```bash
mkdir -p /data
ln -s /data /data2
```

**[PITFALL]** `ls /data2` failed until the symlink was created. If `/data2` does not
exist on the target, create it as a symlink to the real persistent root (here `/data`)
before any deploy step that references `/data2`.

## Step 4 — Launch the container with the NPU-required privilege

This is the step that took the longest to get right.

```bash
docker run --detach \
  --name sglang_server_ssh \
  --hostname sglang_server_ssh \
  --restart unless-stopped \
  --privileged=true \
  --network host \
  --shm-size 64m \
  --volume /data:/data \
  --volume /data:/data2 \
  --volume /mnt:/mnt \
  --volume /usr/local/sbin:/usr/local/sbin \
  --volume /dl2:/dl2 \
  --volume /etc/ascend_install.info:/etc/ascend_install.info \
  --volume /dl:/dl \
  --volume /home:/home \
  --volume /dev:/dev \
  --volume /etc/localtime:/etc/localtime \
  --volume /usr/local/Ascend/driver:/usr/local/Ascend/driver \
  --volume /usr/local/bin/npu-smi:/usr/local/bin/npu-smi \
  --volume /usr/local/dcmi:/usr/local/dcmi \
  sglang-ssh:v0.5.13.post1-cann9.0.0-a3
```

Then start sshd inside the container according to its `-f <config>` config.

**[PITFALL — CRITICAL]** A first attempt launched the container **without**
`--privileged=true`. The result was that NO NPUs were visible inside the container
(`npu_cnt 0`), and `dcmi` returned `-8005` / the driver management channel reported a
failure (`DrvMng ret=4`). Make sure the container is created with `--privileged=true`
whenever NPU driver management channels must be accessible. The working reference
container on 148 and the working vllm containers on 145 are all started privileged.

**[PITFALL]** Do not waste time on a "driver version mismatch" hypothesis when `dcmi`
returns `-8005`: that error was actually the missing `--privileged` flag, not a driver
problem. Confirm with `--privileged=true` first.

**[PITFALL]** The host had the driver at a different CANN build than expected; inside the
container after privilege is fixed, `npu-smi` may still report a `libc_sec.so: cannot
open shared object` on a one-off `npu-smi info`, but this does not affect `torch_npu` /
`sglang`, which keep working. Do not block on it.

## Step 5 — Verify NPU visibility end to end

Run inside the container:

```bash
/usr/local/python3.11.15/bin/python3 -c "import torch,torch_npu; print(torch.__version__); print(torch_npu.npu.device_count())"
```

Expected: `torch 2.10.0` and `16`, plus `Ascend910_9382` for each device.

**[PITFALL]** The default `/usr/bin/python3` in the container may not have `torch` /
`torch_npu` (the CANN/torch install lives under `/usr/local/python3.11.15`). Use the
full path to the Python that carries torch_npu, and `source set_env.sh` first so that
`libhccl.so` etc. resolve.

## Step 6 — Verify ssh reachability to the container

The SSH container is reachable at `root@<target-host>:6222` (host-network mode).
Verify from an external client that the login works and that the NPU probe returns 16
through the ssh session too.

**[PITFALL]** Because `sshd` uses host networking, `docker port <container>` shows
nothing; do not conclude ssh is broken from that. Check the container's sshd
`sshd_config` `Port` and confirm the host is listening on that port.

## Step 7 — Confirm the container is not re-created by accident

The persistent container has `--restart unless-stopped` so it comes back after a host
reboot. Keep it running and do not `docker run` a second copy that would conflict on the
same host-port / network.
